# AGENTS.md

## Назначение
Этот репозиторий — веб-игра-симулятор инвестиций для офлайн-мероприятия. Игра запускается на одном нашем устройстве. Участники играют по очереди. Целевой интерфейс — ноутбук/компьютер; мобильный приоритет отменён пользователем.

Перед любыми изменениями агент должен прочитать:
1. `DECISIONS.md`
2. `PRODUCT_SPEC.md`
3. `GAME_RULES.md`
4. остальные документы по затрагиваемой области.

Если код и документация расходятся, считать `DECISIONS.md` и `PRODUCT_SPEC.md` источником требований и привести реализацию к ним.

## Неподвижные продуктовые решения
- Один компьютер.
- Один игрок одновременно.
- Никаких комнат, кодов подключения и синхронного мультиплеера.
- Каждый новый игрок всегда начинает ровно с **1000 $**.
- Игра состоит ровно из **3 раундов**.
- В новых мероприятиях ровно 6 стартапов: `NovaMind`, `MedFlow`, `VoltX`, `GreenBox`, `AgroPulse`, `OrbitLink`. Старые сохранения используют зафиксированную v1-модель.
- Названия стартапов не переводятся.
- Основной язык интерфейса — русский.
- В правом верхнем углу есть переключатель `RU / EN`.
- Весь остальной интерфейс, описания, показатели, сигналы и события локализуются.
- ИИ в игровой логике отсутствует.
- Рынок определяется заранее подготовленными входами и шоками, рассчитанными по явным формулам на сервере.
- В рамках одного мероприятия используется **один скрытый сценарий для всех игроков**, чтобы лидерборд был сопоставимым.
- Игроки не влияют своими инвестициями на динамику рынка.
- После 3-го раунда результат игрока попадает в общий сохраняемый лидерборд.
- Затем следующий участник начинает новую сессию с 1000 $.
- Есть кнопка `Подвести итоги`.
- После нажатия `Подвести итоги` обязательно запрашивается пароль организатора.
- В окне пароля есть `Подтвердить` и `Отмена`.
- Только правильный пароль завершает мероприятие.
- После завершения новые результаты больше не принимаются.
- Финал показывает анимированное награждение: сначала 3-е место, затем 2-е, затем 1-е.
- После анимации показывается полный итоговый рейтинг.

## Принцип UX
Игрок должен понимать управление без длинной инструкции.

Основное действие:
**посмотреть данные → распределить деньги → подтвердить → увидеть результат.**

Не добавлять без явной необходимости:
- акции и количество бумаг;
- комиссии;
- налоги;
- кредитное плечо;
- сложные финансовые термины;
- аккаунты;
- регистрацию по email;
- роли;
- комнаты;
- WebSocket;
- чат;
- AI.

## Технический базис
Рекомендуемая архитектура MVP:
- Frontend: React + TypeScript + Vite.
- Backend: Node.js + TypeScript + Express.
- БД: SQLite.
- Графики: доступные SVG без обязательной внешней библиотеки.
- Локализация: react-i18next.
- Запуск: локально на одном ноутбуке через браузер.

WebSocket не нужен: одновременно играет один человек, поэтому REST достаточно.

## Деньги
Все расчёты на сервере хранятся в целых центах.
- 1000 $ = `100000`
- 1254.37 $ = `125437`

Не использовать floating-point как источник истины для денег.

В интерфейсе по умолчанию показывать целые доллары. При необходимости точное значение можно показать до центов.

## Сценарии
Будущие доходности и будущие события нельзя отправлять клиенту заранее.
Клиент получает только данные, доступные на текущем этапе.

Один сценарий фиксируется на весь event и хранится сервером.

## Изменение требований
Если пользователь меняет зафиксированное решение:
1. обновить `DECISIONS.md`;
2. обновить связанные документы;
3. только после этого менять реализацию.

Не сохранять в документах устаревшие решения как активные требования.

## Обязательный порядок реализации
- Работать по этапам и идентификаторам элементов из `IMPLEMENTATION_PLAN.md`.
- Перед кодом этапа создать его отчёт в `docs/implementation/` по `TEMPLATE.md`: цель, зависимости, затрагиваемые требования, контракт каждого элемента, критерии приёмки и план проверок.
- После изменения каждого элемента записать в тот же отчёт фактические файлы, поведение, отклонения от плана, результаты проверок и оставшиеся ограничения. Не помечать элемент выполненным до проверки его критериев.
- После завершения этапа обновить его общий статус в `IMPLEMENTATION_PLAN.md` и приложить в отчёте доказательства проверок. Документация не должна выдавать запланированное за выполненное.
- При изменении требований сначала обновить журнал решений и связанную спецификацию, затем план и код. Технические уточнения без изменения поведения явно фиксировать в отчёте этапа.
- Для каждого изменения интерфейса выполнить сценарий в настоящем браузере. Проверить рабочий путь, ошибки и восстановления, релевантные изменению. Скриншоты ключевых состояний просмотреть встроенным зрением; проверка DOM или тестов без просмотра изображения не заменяет визуальную проверку.
- Для серверных и сценарных изменений выполнить автоматические проверки расчётов, переходов, сохранения и отсутствия утечки будущих данных; затем пройти соответствующий пользовательский путь в браузере, когда он доступен.
- В финальной проверке пройти через браузер все новые рыночные сценарии, RU и EN, закрытие мероприятия и последовательную игру нескольких участников. Зафиксировать найденные дефекты и повторно проверить исправления.
- Не записывать пароль, реальные имена игроков, содержимое локальной БД или иные секреты в документацию и артефакты проверки.
