# Архив плана v1 — исторические требования, не активная спецификация

# Подробный план реализации

Статус документа: рабочий план. Этапы 00–04 проверены; этап 05 в работе. Последнее обновление: 2026-09-29.

Этот план разворачивает исходные восемь этапов в проверяемые части. Он не меняет продуктовые решения. Источники требований по приоритету: DECISIONS.md, PRODUCT_SPEC.md, GAME_RULES.md, затем документы по конкретной области. Правила выполнения для будущих изменений закреплены также в AGENTS.md.

## 1. Границы и инварианты

- Один локальный компьютер, один игрок одновременно, последовательные сессии.
- Каждый новый игрок получает ровно 100000 центов, проходит ровно три раунда и работает только с четырьмя фиксированными стартапами.
- Официальные деньги, переходы состояния, рыночные результаты, лидерборд и пароль контролирует сервер.
- Один скрытый сценарий привязан к одному мероприятию. Будущие доходности, события и другие будущие данные отсутствуют в ответах API и в клиентской сборке.
- После третьего раунда результат записывается один раз. После финализации нельзя создать сессию или принять новый результат.
- Русский по умолчанию; весь интерфейс и сценарный текст имеют RU/EN, названия четырёх стартапов неизменны.
- Нет ИИ, комнат, синхронного мультиплеера, WebSocket, аккаунтов, акций, комиссий, налогов и кредитного плеча.
- Этап 00 был документальным. Реализация приложения началась с этапа 01 и продолжается по этой последовательности.

## 2. Порядок работы и документация

Для каждого этапа NN до изменения кода создаётся docs/implementation/NN-название.md по docs/implementation/TEMPLATE.md. Каждый элемент из таблиц ниже получает в этом файле отдельный подраздел с тем же идентификатором.

Для каждого элемента фиксируются:

1. Требование и связь с исходными документами.
2. Конкретный контракт: поведение, данные, состояния, тексты или визуальный результат.
3. Затронутые файлы и принятые технические решения.
4. Положительные, граничные и ошибочные проверки.
5. Фактический результат: команды, тесты, браузерные шаги, снимки и визуальные наблюдения.
6. Дефекты, исправления, повторная проверка и остаточные ограничения.
7. Статус: запланирован, в работе, проверен или заблокирован.

Отчёт этапа открывается до кода и закрывается после проверки всех элементов. Статус этапа в этом плане меняется только после закрытия отчёта. Если на этапе выясняется изменение продукта, сначала обновляются DECISIONS.md и связанные требования, затем этот план, затем код. Технические уточнения без изменения продукта вносятся в отчёт и подходящий технический документ.

Доказательства хранятся в docs/implementation/evidence/ с именами по этапу, элементу, сценарию, языку и размеру экрана. Если браузерный инструмент показывает снимок только внутри журнала задачи и не предоставляет файл, отчёт может сослаться на вкладку/маршрут и записать фактическое визуальное наблюдение. Снимок без записанного визуального просмотра не считается проверкой. Не сохранять в доказательствах пароль, настоящие имена игроков и локальную БД.

## 3. Общие критерии завершения элемента

- Поведение совпадает с контрактом и инвариантами; новые функции не выходят за пределы MVP.
- Ошибки показываются понятным локализованным текстом, состояние после них остаётся корректным.
- Денежные значения на сервере целочисленные; операции с БД, меняющие итог, атомарны.
- Для API проверены успешный и запрещённый переходы, повторы запросов и публичная форма ответа.
- Для UI выполнен путь в настоящем браузере; ключевые состояния просмотрены через встроенное зрение по снимкам экрана. Для нового экрана проверены RU и EN, клавиатура, desktop и узкий экран.
- Документация элемента отражает фактическую реализацию и доказательства. Обнаруженный дефект исправлен и повторно проверен либо явно оставлен как блокер этапа.

## 17. Решения, которые нужно уточнить до соответствующего кода

Эти пункты не меняют зафиксированное поведение и не блокируют текущий этап документации:

- Как поступать с незавершённой сессией при попытке финализации: планируется отвергать финализацию с понятной ошибкой до завершения или операторского сброса сессии. Это предотвращает скрыто потерянный результат.
- Как оператор начинает следующее мероприятие после закрытия текущего: планируется локальная команда без отдельной админ-страницы; старые event сохраняются в БД и не показываются в UI.
- Одинаковые имена в пределах одного event: DATA_MODEL.md рекомендует запрет. Планируется проверка совпадения после trim без учёта регистра; при ином пожелании правило надо закрепить до этапа 04.
- Точные места при ничьей: планируется соревновательная нумерация (1, 1, 3) и совместный показ обладателей одинакового места на соответствующем шаге награждения.

Если пользователь уточнит один из этих пунктов, сначала обновить решения и связанные документы, затем соответствующие элементы плана.
