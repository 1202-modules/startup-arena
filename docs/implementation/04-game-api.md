# Этап 04 — серверный игровой цикл

## Паспорт этапа

- Статус: проверен.
- Дата начала: 2026-09-29.
- Зависимости: этапы 02 и 03 проверены.
- Требования: DECISIONS.md; PRODUCT_SPEC.md, разделы 3–6; GAME_RULES.md, разделы 1–9; ARCHITECTURE.md, разделы 4–9; DATA_MODEL.md; TESTING.md; IMPLEMENTATION_PLAN.md, этап 04.
- Цель: реализовать серверный цикл трёхраундовой сессии, валидировать каждое изменение и сохранять результаты атомарно в целых центах.
- Что не входит: React-экраны (этапы 05–07), пароль финализации (этап 08), анимация награждения (этап 09).
- Модель состояния: `participants.current_round`, наличие `round_results` и `portfolios.confirmed` определяют DECISION/RESULT; `participants.status=COMPLETED` завершает сессию. Отдельное поле состояния, дублирующее эти данные, не добавляется.
- Начальный портфель: 100000 центов в cash. После успешного результата новый черновик наследует фактические значения четырёх позиций и cash предыдущего раунда; пользователь может перераспределить их перед следующим подтверждением.
- Имена: trim и Unicode NFC для отображаемого имени; длина 2–24 Unicode code point; поиск дублей — NFKC + `toLocaleLowerCase("ru-RU")`. Значение имени сохраняется как текст и не интерпретируется как HTML.
- Техническая миграция: схема повышается с версии 1 до 2 — добавляется `participants.name_key`, уникальность имени в event и частичный уникальный индекс одной незавершённой сессии. Старые события и участники остаются на месте.
- Деньги: входы — только JSON safe integer cents; сумма пяти частей портфеля обязана точно равняться текущему капиталу; до округления используются BigInt промежуточные значения.
- Публичные DTO не содержат event ID, scenario ID, сценарий целиком, доходности будущих раундов или чужие распределения. Будущие исходы берутся с сервера только после подтверждения своего текущего раунда.

## Элемент 04.1 — машина состояний

- Статус: проверен.
- Источник: ARCHITECTURE.md, раздел 9; GAME_RULES.md, раздел 5; IMPLEMENTATION_PLAN.md, 04.1.
- Контракт: решения 1/2/3 следуют только `DECISION → RESULT`; результаты 1/2 следуют только в следующий `DECISION`; результат 3 следует только в `COMPLETED`. Раунд игрока всегда 1..3, и второй текущий участник того же мероприятия не допускается.
- Приёмка: допустимые переходы создают только требуемые записи; прямой переход, повторное продвижение, подтверждение не текущего раунда и действия после завершения не меняют БД.
- План: `server/src/sessions/session-store.ts`, частичный unique index одной активной сессии.
- Факт и проверка: `current_round`, `round_results`, `portfolios.confirmed` и `status` задают фазу без повторного state-поля. Проверены успешные переходы 1→2→3→COMPLETED, запрет раннего next/complete и подтверждения не текущего раунда; неудачные переходы не оставили result/confirmation.

## Элемент 04.2 — создание участника

- Статус: проверен.
- Источник: DECISIONS.md; PRODUCT_SPEC.md, раздел 3; GAME_RULES.md, раздел 1; DATA_MODEL.md, раздел «Имена»; IMPLEMENTATION_PLAN.md, 04.2.
- Контракт: `POST /api/sessions` принимает `{ name, language }`; валидирует язык RU/EN и имя после trim; создаёт участника со статусом `IN_PROGRESS`, капиталом/cash `100000` и черновиком раунда 1 `all cash`. Новая сессия запрещена при закрытом event, активном участнике или имени, уже занятом в event без учёта регистра/Unicode compatibility.
- Приёмка: пустое/короткое/длинное имя, неверный язык, повторное имя и параллельная сессия получают точный API error; HTML-подобное имя остаётся текстом; после финализации создать нельзя.
- План: `server/src/participants/name.ts`, миграция v2, `server/src/sessions/session-store.ts`.
- Факт и проверка: `POST /api/sessions` создаёт 100000 центов в cash и одну активную сессию. Проверены границы 2/24 символа, неверный язык, NFKC-дубликат после завершения, Unicode trim/NFC, HTML-подобный текст, запрет второго активного и старта после FINALIZED. Индекс БД повторяет ключевые уникальности.
- Уточнение 2026-10-01: `server/src/sessions/session-store.ts` ищет последнее событие по `rowid DESC`, как и event-store. Тест с одинаковыми `created_at` подтвердил, что новая сессия записывается именно в новый event.

## Элемент 04.3 — чтение сессии и восстановление

- Статус: проверен.
- Источник: PRODUCT_SPEC.md, разделы 3–5; ARCHITECTURE.md, session API; IMPLEMENTATION_PLAN.md, 04.3.
- Контракт: `GET /api/sessions/:id` возвращает только один session ID: собственное состояние, текущий черновик, текущие публичные наблюдения в DECISION или текущий результат в RESULT, раскрытые предыдущие раунды, а также капитал и свободные деньги. Для COMPLETED сохраняются последний результат, конечный капитал и актуальное место.
- Приёмка: повторное чтение в каждой фазе возвращает сохранённое состояние; неизвестный ID — 404; payload не содержит чужие портфели, scenario ID или будущие сигналы/результаты.
- План: shared DTO `SessionResponse`, `SessionRoundResult`; projections из этапа 03.
- Факт и проверка: `GET /api/sessions/:id` проверен в DECISION, RESULT, после next и COMPLETED; reload-equivalent повторное чтение сохранило статус, капитал, черновик и место. 404 для неизвестного ID. Сериализованные ответы полного цикла всех трёх сценариев не содержали scenario ID, будущих событий/доходностей или чужого портфеля.

## Элемент 04.4 — черновик портфеля

- Статус: проверен.
- Источник: GAME_RULES.md, разделы 2, 3 и 6; DATA_MODEL.md, portfolios; IMPLEMENTATION_PLAN.md, 04.4.
- Контракт: `PUT /api/sessions/:id/portfolio` принимает `startupAmountsCents` по четырём неизменным брендам и `cashCents`. Все значения — safe integer ≥0; сумма ровно текущий капитал. Обновляется только черновик текущего раунда до подтверждения.
- Приёмка: проверить all cash, одну позицию, 4 компании, точные центы, отрицательные/дробные/слишком большие числа, неправильную сумму, пропущенный или лишний startup key, обновление черновика и запрет после confirm.
- План: проверка формы на API-границе, запись в транзакции; сумма также закрыта SQL-ограничениями по типу и неотрицательности каждого поля.
- Факт и проверка: ровно четыре известных startup key, safe integer ≥0 и точная сумма проверяются до обновления; переданы all-cash, распределения по компаниям и половинные центы. Отрицательные, дробные, небезопасные, неизвестные/пропущенные ключи и неверные суммы вернули 400, черновик остался без изменений. После confirm изменение возвращает 409.

## Элемент 04.5 — атомарное подтверждение

- Статус: проверен.
- Источник: GAME_RULES.md, раздел 4; ARCHITECTURE.md, разделы 4–5; DATA_MODEL.md, round_results; IMPLEMENTATION_PLAN.md, 04.5.
- Контракт: `POST /api/sessions/:id/rounds/:round/confirm` валидирует фазу, текущий round и event OPEN; фиксирует черновик, применяет серверные bps текущего scenario/round, округляет каждую компанию до целого цента half-up, переносит cash без изменения, сохраняет результат и обновляет капитал одним `BEGIN IMMEDIATE` transaction.
- Приёмка: совпадают новые значения по компаниям, прибыль/убыток и капитал; неправильный переход не создаёт ни portfolio confirmation, ни result; повторный confirm текущего раунда возвращает прежний результат и не начисляет второй раз. После финализации запрос отклоняется.
- План: общий денежный helper, сохранение bps по четырём компаниям и публичный reveal только запрошенного раунда.
- Факт и проверка: вся операция выполняется `BEGIN IMMEDIATE`; по 3 раунда на каждый из трёх scenario ID результат сравнивался с ожидаемыми return bps и BigInt формулой. Отдельно проверено округление 0.5 цента вверх, cash-only без изменения капитала, обновление cash/capital и сохранение только четырёх текущих bps.

## Элемент 04.6 — следующий раунд

- Статус: проверен.
- Источник: PRODUCT_SPEC.md, раздел 3; GAME_RULES.md, раздел 5; IMPLEMENTATION_PLAN.md, 04.6.
- Контракт: `POST /api/sessions/:id/next` доступен только после результата текущего раунда 1 или 2. Атомарно увеличивает номер, создаёт новый черновик из рассчитанных значений предыдущих четырёх позиций и cash; доходности уже завершённых раундов появляются в графической истории.
- Приёмка: редактирование распределения доступно с новым капиталом; next до confirm, повторный next, next после 3-го раунда и next после закрытия event отклоняются без изменения БД.
- Факт и проверка: новый черновик содержит полученные значения четырёх компаний и прежний cash, current_round увеличивается ровно на 1. Проверены next до confirm, повторный next логикой состояния, раунд 3 и закрытый event; все запрещённые переходы оставляют БД прежней.

## Элемент 04.7 — завершение участника

- Статус: проверен.
- Источник: PRODUCT_SPEC.md, раздел 3, «Финал игрока»; DATA_MODEL.md, `participants.final_capital_cents`; IMPLEMENTATION_PLAN.md, 04.7.
- Контракт: `POST /api/sessions/:id/complete` доступен только после результата раунда 3; записывает `COMPLETED`, `finished_at` и точный final capital. Возвращает соревновательное место в текущем рейтинге. Повтор при OPEN event не создаёт новую запись.
- Приёмка: нельзя завершить участника до результата 3-го раунда; конечный капитал совпадает с current capital; повтор безопасен; ранги при ничьей одинаковые; новый participant после завершения получает отдельные 100000 центов.
- Факт и проверка: COMPLETED и final capital пишутся один раз; повтор возвращает тот же DTO. Место — число более крупных итогов + 1, поэтому tie rank совпадает с лидербордом; новый участник того же event начинает с 100000 и тем же decision market.

## Элемент 04.8 — денежные границы

- Статус: проверен.
- Источник: GAME_RULES.md, разделы 1 и 4; IMPLEMENTATION_PLAN.md, 04.8.
- Контракт: никакой floating point не используется для валидности/итога денег; JSON принимаются только safe integer cents; умножение и суммы рассчитываются BigInt с проверкой диапазона результата.
- Приёмка: кейсы половины цента округляются вверх по правилу; bps `-10000` даёт нулевую стоимость позиции; bps `< -10000`, отрицательный портфель, дробная сумма, переполнение и несходящаяся сумма отклоняются.
- Факт и проверка: валидатор принимает лишь JSON safe integers, сравнение суммы и расчёт результата используют BigInt, half-up выполнен как `(amount * (10000 + bps) + 5000) / 10000`; все три scenario data валидируются при старте. Для позиции 50¢ с доходностью +11% проверено 56¢. Нижняя граница −10000 проверена в schema/scenario suite; меньшие bps запрещены каталогом и БД.

## Элемент 04.9 — повторы и конкурирующие запросы

- Статус: проверен.
- Источник: TESTING.md, раздел 8; DATA_MODEL.md, уникальности; IMPLEMENTATION_PLAN.md, 04.9.
- Контракт: транзакции `BEGIN IMMEDIATE`, UNIQUE participant/round и подтверждённое состояние превращают confirm/next/complete в один переход даже при повторе. Повтор уже принятого confirm возвращает записанный результат; следующий round или complete не начисляют новое значение.
- Приёмка: одновременно отправленные операции не создают дубликаты, а подсчёт `round_results` остаётся один на round; REST-ответ каждой попытки соответствует сохранённому состоянию.
- Факт и проверка: параллельные browser `fetch` для каждого confirm на Scenario 03 вернули одинаковый сохранённый результат; последовательные повторные confirm сделаны на всех трёх scenario ID. UNIQUE `(participant_id, round_no)`, partial active index и immediate транзакции остаются дополнительной защитой.

## Элемент 04.10 — ошибки и контракт

- Статус: проверен.
- Источник: ARCHITECTURE.md, REST API; IMPLEMENTATION_PLAN.md, 04.10.
- Контракт: ошибочные ответы остаются `{ error: { code, message } }`: `VALIDATION_ERROR` (400), `SESSION_NOT_FOUND` (404), `INVALID_STATE`, `EVENT_FINALIZED`, `SESSION_ALREADY_ACTIVE`, `DUPLICATE_NAME` (409), `INTERNAL_ERROR` (500). Ошибка базы не раскрывает SQL, путь файла или содержимое сценария.
- Приёмка: неправильные параметры, неправильная фаза, отсутствующая сессия, уже закрытый event, сломанный JSON и внутреннее исключение возвращают подходящий статус и код; БД после запроса не меняется, утечки future данных нет.
- Факт и проверка: malformed JSON — 400 `VALIDATION_ERROR`, неизвестный ID — 404 `SESSION_NOT_FOUND`, ранний next — 409 `INVALID_STATE`, финализированная event блокирует все write routes с 409 `EVENT_FINALIZED`; внутренние ошибки получают общий `INTERNAL_ERROR` без SQL/путей/сценария. Браузерная консоль warning/error пуста.

## Сквозные результаты этапа

- `npm test` — прошёл: shared contract 1/1; server suite 4/4 файлов (database, fixture, scenario catalog, sessions); клиент/server/shared production build выполнен.
- `npm run typecheck` — прошёл для shared, server и client.
- `npm test` включает сценарии всех трёх scenario ID на отдельных временных SQLite-файлах; браузерный same-origin HTTP runner по 34 шага прошёл для Scenario 01, 02, 03; Scenario 03 дополнительно прошёл конкурентный confirm (37 шагов).
- Миграция v1→v2 проверена на данных: legacy name остаётся, нормализованный ключ рассчитывается, duplicate NFKC-каталог отменяет миграцию с rollback.
- Временный браузерный тестовый сервер работал на `http://127.0.0.1:3001`; окно CUA 1579×960. Снимок страницы полного прогона просмотрен встроенным зрением: список статусов и итог читаемы, обрезания/наложения нет. Console error/warn: `[]`. Тестовая БД хранилась только в `/tmp`.
- Стартовая игровая страница после сборки снова открыта и подключена к серверу; интерфейс приложения на этом этапе не менялся. Полные игроковые экраны и их визуальная приёмка относятся к этапам 05–07 и 10.

## Фактические результаты

Этап закрыт: миграция схемы, маршруты игрового цикла, денежная математика, идемпотентность, leaderboard и приватность сценария реализованы и проверены. Временный browser harness в `client/dist` удалён финальной Vite-сборкой; в исходниках приложения его нет. Ограничение миграции: если в старой БД обнаруживаются уже занятые нормализованные имена, запуск остановится безопасной ошибкой вместо автоматического переименования данных.
