# Этап 02 — БД, мероприятие и рейтинг

## Паспорт этапа

- Статус: проверен.
- Дата начала: 2026-09-29.
- Зависимости: этапы 00 и 01 проверены.
- Требования: DECISIONS.md; PRODUCT_SPEC.md, разделы 3 и 6–7; GAME_RULES.md, разделы 8–9; ARCHITECTURE.md, разделы 3–8; DATA_MODEL.md; IMPLEMENTATION_PLAN.md, этап 02.
- Цель: добавить локальное хранилище SQLite, устойчивый event lifecycle и приватный публичный рейтинг.
- Что не входит: игровые сессии и запись результатов (этап 04), полные данные сценариев (этап 03), UI рейтинга (этап 06), финализация (этап 08).
- Предварительное решение по уточнению из плана: новый event создаётся локальной операторской командой только после закрытия предыдущего. Если придёт другое пожелание, обновить требования до выпуска этапа.
- Сценарий выбирается случайно один раз при создании event и остаётся неизменным. Каталог на этом этапе содержит только 3 фиксированных ID из SCENARIOS.md; содержимое будет добавлено на этапе 03.
- Техническое решение: использовать `better-sqlite3` и его типы, транзакции SQLite выполнять синхронно внутри коротких callback. Версия драйвера фиксируется lockfile; это оставляет детали SQL за серверной границей и не добавляет клиентских зависимостей.
- Секреты и персональные данные: тестовые имена синтетические; содержимое тестовой БД временное и не сохраняется в docs.

## Элемент 02.1 — схема SQLite

- Статус: проверен.
- Источник: DATA_MODEL.md; GAME_RULES.md; IMPLEMENTATION_PLAN.md 02.1.
- Контракт: таблицы `events`, `participants`, `portfolios`, `round_results`; `STRICT`-таблицы; внешние ключи; ограничения статусов, языка и раундов 1..3; уникальная пара участник/раунд; суммы неотрицательны и целые; возврат не ниже −10000 bps. Портфель хранит распределение в центах, а согласованность его суммы с капиталом проверяется игровым API на этапе 04.
- Приёмка: миграция по `user_version` идемпотентна, FK включены для каждого подключения, БД переживает повторное открытие, записи с нарушенными ограничениями отклоняются.
- План файлов: `server/src/db/migrations.ts`, `server/src/db/database.ts`, `server/src/events/event-store.ts`, `server/test/database.test.js`.
- Факт: созданы все четыре таблицы как `STRICT`; миграция версии 1 идемпотентна; подключение включает FK, WAL для файловой БД и busy timeout. Проверки реально отклоняют отрицательные суммы, неверный раунд, дубли portfolio/result, несуществующий FK, доходность ниже −10000 bps и второй `OPEN` event. Тесты: `migration is idempotent and enforces foreign keys and domain constraints`.

## Элемент 02.2 — жизненный цикл мероприятия

- Статус: проверен.
- Источник: DECISIONS.md, раздел «Сценарии и честность»; SCENARIOS.md; IMPLEMENTATION_PLAN.md 02.2.
- Контракт: при пустой БД атомарно создать одно `OPEN`-мероприятие с UUID, ISO-датой и одним случайно выбранным ID из `scenario-01`..`scenario-03`; при рестарте выбрать последнее мероприятие и сохранить исходный `scenario_id`. Частичный уникальный индекс допускает не более одного `OPEN`-мероприятия.
- Приёмка: повторная инициализация не создаёт второй event; значение сценария остаётся прежним; клиентский ответ и журнал запуска не содержат `scenario_id`; после `FINALIZED` новый event не создаётся автоматически.
- Факт: `ensureCurrentEvent()` записывает событие и один случайный ID сценария атомарно; повторный вызов сохраняет UUID и scenario ID. Тест после перевода последнего event в `FINALIZED` подтверждает, что инициализация возвращает его же и не добавляет новое мероприятие. В публичной проекции и на странице сценарий отсутствует.
- Уточнение 2026-10-01: `server/src/events/event-store.ts` выбирает последнее событие по SQLite `rowid DESC`. Тест принудительно выравнивает `created_at` старого и нового события и подтверждает, что возвращается именно новое; прежняя сортировка `created_at, id` могла выбрать старый UUID при совпадении миллисекунды.

## Элемент 02.3 — создание следующего мероприятия

- Статус: проверен.
- Источник: DECISIONS.md; PRODUCT_SPEC.md, раздел 9; IMPLEMENTATION_PLAN.md 02.3.
- Контракт: `npm run event:new` создаёт новое `OPEN`-мероприятие, когда последнее мероприятие `FINALIZED`; прежние строки сохраняются. До команды каталог должен быть собран.
- Приёмка: команда отказывает при текущем `OPEN`-мероприятии и при любом незавершённом участнике; успешная команда создаёт новый UUID, сценарий и время.
- Уточнение 2026-10-01: при создании следующего события в ту же миллисекунду оно остаётся последним независимо от порядка UUID; это проверено `server/test/database.test.js`. Фактические файлы исправления: `server/src/events/event-store.ts`, `server/src/sessions/session-store.ts`, `server/test/database.test.js`.
- Техническое решение: без отдельной админ-страницы; команда реализуется собранным CLI `server/dist/cli/create-event.js`, подключается корневым npm script и описывается в README.
- Факт: `npm run event:new` на временной БД успешно открыл второе мероприятие после закрытого первого; та же команда на открытом event завершилась кодом 1 с понятным сообщением. Unit-проверка отдельно удостоверилась, что при незавершённом участнике в финализированном event новая запись не появляется.

## Элемент 02.4 — транзакционный доступ к данным

- Статус: проверен.
- Источник: ARCHITECTURE.md, раздел 4; IMPLEMENTATION_PLAN.md 02.4.
- Контракт: миграция применяется транзакционно; создание event также транзакционно; включены foreign keys, WAL и ограниченный busy timeout; родительский каталог файла БД создаётся автоматически.
- Приёмка: ошибка внутри транзакции откатывает вставки; частичный уникальный индекс не позволяет двум командам открыть два события.
- Факт: миграция и event-операции используют транзакции `BEGIN IMMEDIATE`; неуспешный переход `event:new` оставляет число событий равным одному. Частичный индекс независимо защищает от второго открытого мероприятия.

## Элемент 02.5 — публичный event API

- Статус: проверен.
- Источник: ARCHITECTURE.md, раздел 7; PRODUCT_SPEC.md, разделы 3 и 6; IMPLEMENTATION_PLAN.md 02.5.
- Контракт: `GET /api/event` возвращает `status`, `completedCount` и `leaderboard: { place, name, finalCapitalCents }[]`; не возвращает `scenario_id`, портфели, незавершённых участников, доходности, пароль организатора или внутренний UUID event.
- Приёмка: ответ корректен для `OPEN`/`FINALIZED` и пустого рейтинга; тест намеренно вносит приватные поля в БД и подтверждает, что они не сериализуются.
- Факт: API подключён в `server/src/app.ts`; `client/src/App.tsx` выполняет GET `/api/event` вместе с health check и считает подключение успешным только при корректной публичной форме ответа. Публичная функция проверена с завершёнными и незавершённым участниками; тело содержит только статус, число завершивших и публичные записи. Скрытый scenario ID, event ID и портфели не сериализуются.

## Элемент 02.6 — ранжирование и равные места

- Статус: проверен.
- Источник: DECISIONS.md, раздел «Лидерборд»; GAME_RULES.md, раздел 9; IMPLEMENTATION_PLAN.md 02.6.
- Контракт: точная сортировка по `final_capital_cents DESC`; одинаковый итоговый капитал получает одинаковое соревновательное место (1, 1, 3); внутри равенства стабильный порядок по `finished_at`, затем ID.
- Приёмка: незавершённые участники не отображаются; точные центы определяют порядок независимо от округлённого UI.
- Факт: тест использует 125437, 125437 и 100001 цент: два первых игрока делят место 1, следующий получает место 3; порядок внутри равенства стабилен по времени завершения и ID. Активный игрок не включён.

## Элемент 02.7 — сохранение

- Статус: проверен.
- Источник: PRODUCT_SPEC.md, раздел 6; DATA_MODEL.md; TESTING.md, разделы 4 и 8; IMPLEMENTATION_PLAN.md 02.7.
- Контракт: выбранное мероприятие и рейтинг вычисляется из файловой SQLite БД и переживает закрытие/повторный запуск сервера; `FINALIZED` остаётся закрытым.
- Приёмка: два подключения к одной тестовой файловой БД видят одно мероприятие и рейтинг; после закрытия первого соединения и открытия второго сценарий и строки рейтинга неизменны.
- Факт: тест создаёт вложенный каталог и файловую БД в системной временной папке, сверяет две одновременные связи, закрывает их и открывает файл снова. UUID мероприятия, scenario ID и рейтинг совпадают. Временный каталог удаляется тестом; `data/game.sqlite` в репозиторий не создавался.

- Автоматические тесты на пустую БД, миграцию, ограничения, повторный запуск, создание следующего event, сортировку, ничьи и скрытие приватных данных.

Снимок после изменения интерфейса этапа 01 просмотреть встроенным зрением; визуальную регрессию каркаса отметить.

- Общие команды завершились успешно: `npm test`, `npm run typecheck`, `npm run build`; `git diff --check` выполнить нельзя — каталог проекта не содержит Git-репозитория.
