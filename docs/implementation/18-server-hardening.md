# Этап 18 — Базовая защита сервера

## Паспорт этапа

- Статус: выполнен. Дата: 2026-10-02.
- Зависимости: этап 17 развернут; Ubuntu 22.04; Docker Compose; Fail2ban отсутствует, UFW неактивен.
- Цель: включить SSH brute-force бан, ограничить частые игровые запросы и убрать открытый HTTP доступ к приложению напрямую.
- Область: только сервис Startup Arena и SSH защита хоста. Не менять firewall других приложений и хостовый Nginx.
- Исходные слушатели: 22/80/443/3000/3001/8080/10050/3443; Docker публикует 3001, 8080 и 3443. Порт игры 3443 принимает HTTPS через контейнерный Nginx.
- UFW оставлен неактивным: хост обслуживает несколько других публичных приложений, для которых нет подтверждённой матрицы разрешённых портов. Порт игры 3001 закрыт напрямую отдельной привязкой loopback.
- Проверки не должны создавать реальные игровые записи или менять данные участников.
- Секреты: пароль хоста и конфигурация `.env` в отчёт не включать.

## 18.1 — SSH brute-force защита

- Статус: локальная конфигурация подготовлена; требуется применить и проверить на сервере.
- Контракт: Fail2ban банит источник после 5 неудачных SSH входов за 10 минут на 1 час; существующие способы SSH-входа сохраняются.
- Факт: добавлен `ops/fail2ban/sshd.local` (systemd journal + nftables). По просьбе пользователя парольный и root SSH-вход восстановлены к прежним эффективным настройкам (`PasswordAuthentication yes`, `PermitRootLogin yes`).
- Проверка: `fail2ban-client -t` — OK; сервис enabled/active, jail `sshd` активен (5 попыток, 600 секунд, 3600 секунд); Fail2ban заблокировал 2 источника. После восстановления `sshd -t` — OK, `sshd -T` показывает `PasswordAuthentication yes`, `PermitRootLogin yes`; reload SSH завершился, новая SSH-сессия по ключу успешна.

## 18.2 — Лимиты игровых HTTP запросов

- Статус: локальная конфигурация подготовлена; требуется применить и проверить на сервере.
- Контракт: адрес организатора и создание сессии ограничены по IP с ответом 429 сверх заданного burst; штатные игровые запросы и HTTPS остаются доступны.
- Факт: `nginx/nginx.conf` задаёт 5 запросов/минуту для organizer login/finalize и 30 запросов/минуту для создания сессий; bursts 4 и 50, ответ при превышении — 429. Остальные маршруты без лимита.
- Проверка: `docker compose config -q`, `nginx -t` и `nginx -T` в контейнере успешны; HTTPS `/api/health` отвечает 200. Сессии не создавались.

## 18.3 — Прямая HTTP публикация

- Статус: локальная конфигурация подготовлена; требуется применить и проверить на сервере.
- Контракт: контейнер приложения доступен с хоста через `127.0.0.1:3001`, а извне через HTTPS proxy на 3443; маршруты других приложений не меняются.
- Факт: Compose публикует `127.0.0.1:3001`; все остальные публичные listeners оставлены без изменений.
- Проверка: `docker compose ps` и `ss -ltn` показывают только `127.0.0.1:3001`; локальный HTTP и HTTPS health отвечают 200; внешний запрос к `:3001` не получает HTTP-ответ. Публичные порты 22/80/443/3000/8080/10050/3443 сохранились.
- Откат: Compose и Nginx конфиги сохранены на хосте в `/home/clubfest/platypus_backups/security-20261002`; SSH и Fail2ban конфиги сохранены в root-only каталоге `/root/server-hardening-20261002`.
