# Исследование и контракт учебной модели рынка

Дата проверки источников и кандидата реализации: 2026-10-01. Область: `server/src/scenarios/model.ts` и `generated.ts`. Документ описывает математические основания, допущения и проверки; сам по себе не подтверждает прохождение автоматических или браузерных тестов.

## 1. Что моделируется

Это учебная детерминированная модель шести вымышленных компаний: NovaMind, MedFlow, VoltX, GreenBox, AgroPulse и OrbitLink. Игрок управляет распределением 1000 $, проходит три раунда на одном ноутбуке и не меняет бизнес компаний. Один скрытый заранее вычисленный сценарий закрепляется за всем мероприятием. Каждый раунд соответствует одному кварталу; финансовая история до игры и результаты раундов вычисляются одним движком.

Связь показателей: платящие клиенты и средний платёж определяют выручку; переменные и постоянные денежные расходы определяют операционный поток; вложения уменьшают денежный запас; оценка операционного бизнеса вместе с запасом денег и обязательствами определяет стоимость компании. Доходность инвестиции выводится из отношения двух оценок. Проценты доходности не являются входными данными сценария.

Это модель поведения бизнеса и учебной переоценки, а не точный прогноз биржевых цен. Реальные котировки также зависят от ранее ожидавшихся результатов, ликвидности, состава инвесторов, ставок, правил финансирования и других факторов. Приведённые ниже реальные отчёты иллюстрируют отдельные связи и масштабы изменений. Они не устанавливают игровые коэффициенты и не доказывают соответствие игровой доходности доходности реальных акций.

## 3. Единицы, состояние и шоки

Все денежные величины — целые центы USD; `B = 10000` означает единицу для bps. Один доллар = 100 центов. `multipleBps = 28000` означает множитель годовой выручки 2,8, а не доходность 280%.

Состояние:

```ts
type BusinessState = {
  customers: number;       // платёжные единицы, целое число
  arpuCents: number;       // платёж за единицу за месяц
  unitCostCents: number;   // переменные денежные затраты за единицу за месяц
  fixedCostsCents: number; // постоянные денежные расходы за месяц
  cashCents: number;       // остаток доступных денег
  debtCents: number;       // номинальный дефицит финансирования
  growthBps: number;       // проявившийся модельный квартальный темп спроса
  multipleBps: number;     // множитель годовой выручки для терминальной оценки
};
type BusinessParameters = {
  discountBps: number;         // фиксированный квартальный дисконт
  maintenanceCapexBps: number; // регулярные вложения как доля квартальной выручки
};
type BusinessShock = {
  customerGrowthBps: number;
  arpuChangeBps: number;
  unitCostChangeBps: number;
  fixedCostChangeBps: number;
  capexCents: number;          // только ДОПОЛНИТЕЛЬНЫЕ разовые вложения
  multipleChangeBps: number;   // отдельное изменение рыночной оценки перспектив
};
```

`customers` требует определения в описании компании. Рекомендуемые единицы: NovaMind — платящие организации/подписки; MedFlow — подключённые клиники; VoltX — активные корпоративные сервисные подключения к системам хранения; GreenBox — обслуживаемые торговые/логистические точки; AgroPulse — хозяйства с действующим обслуживанием; OrbitLink — корпоративные спутниковые подключения. Все эти модели являются сервисными или гибридными: доход от разовой продажи оборудования отдельно не моделируется.

Если сохранить в интерфейсе общий ярлык «Клиенты», описание должно объяснять единицу. Уход одной торговой сети может отключить сотни её точек; уход одного из 750 независимых юридических лиц не уменьшает их число на 34%. В промышленной модели «получены заказы» не означает автоматически «поставка выполнена и признана выручка»: событие должно говорить о начале обслуживаемых подключений или явно устанавливать немедленное признание в учебной модели.

Шоки — фиксированные экзогенные изменения, а не случайные числа и не функции вложений игрока. Несколько одновременно заданных шоков описывают одно событие: например, перенос запуска может сократить подключения, увеличить разовые вложения и изменить ожидаемую устойчивость бизнеса. Изменение multiple допустимо лишь с отдельным объяснением пересмотра долгосрочных перспектив; его нельзя подбирать для достижения заранее желаемого процента доходности.

## 4. Округление и переход состояния

Округление половины до ближайшего целого от нуля; все промежуточные произведения выполняются как BigInt:

```ts
const B = 10000n;
function roundDiv(n: bigint, d: bigint): bigint {
  if (d <= 0n) throw new RangeError("Positive divisor required");
  return n < 0n ? -((-n + d / 2n) / d) : (n + d / 2n) / d;
}
function applyBps(x: bigint, bps: bigint): bigint {
  if (x < 0n || bps < -B) throw new RangeError("Invalid factor");
  return roundDiv(x * (B + bps), B);
}
```

Для каждого периода сначала обновляются клиенты, ARPU, unitCost и fixedCosts. Принято, что новые условия действуют весь квартал; позднее вступление договора в силу не моделируется.

```text
Cnext = applyBps(C, customerGrowthBps)
Anext = applyBps(A, arpuChangeBps)
Unext = applyBps(U, unitCostChangeBps)
Fnext = applyBps(F, fixedCostChangeBps)
Mnext = applyBps(M, multipleChangeBps)
Rnext = Cnext * Anext                         // выручка за месяц
Enext = Cnext * Unext + Fnext                 // денежные расходы за месяц
OCFnext = 3 * (Rnext - Enext)                 // операционный поток за квартал
maintenance = roundDiv(3 * Rnext * maintenanceCapexBps, B)
FCFnext = OCFnext - maintenance - extraCapex  // поток до финансирования
netCashNext = cash - debt + FCFnext
cashNext = max(netCashNext, 0)
debtNext = max(-netCashNext, 0)
```

Последние две строки разлагают знаковую величину на деньги и обязательства; это не исчезновение убытка. Инвариант:

`cashNext - debtNext = cash - debt + OCFnext - maintenance - extraCapex`.

Например, денежный запас 10 $, обязательства 0 $, отрицательный FCF −15 $ дают cash 0 $, debt 5 $. Следующий FCF +3 $ уменьшает debt до 2 $, не создавая денег. Следующий +8 $ погашает 2 $ и оставляет cash 6 $.

Здесь принято автоматическое финансирование дефицита и погашение обязательств при появлении денег. Проценты, срок погашения, лимит кредита и отдельная комиссия отсутствуют. Это упрощение учёта компании; игрок не получает кредит или плечо. `debtCents` нельзя называть полноценной реалистичной кредитной моделью. Сценарии релиза должны избегать бесконечного финансирования неплатёжеспособного бизнеса: учитывать дефицит в оценке, проверять положительную стоимость продолжающих работать компаний и отдельно отклонять некорректные сценарии.

Месячные expenses — именно денежные операционные расходы. Поэтому `3*(R-E)` используется как OCF только при допущениях отсутствия налогов, амортизации, дебиторской задолженности, запасов и отсрочек. Капитальные вложения отражаются отдельно и не входят туда второй раз. Это существенное отличие от полной финансовой отчётности.

## 5. Оценка и доходность

Используем комбинированную учебную оценку: четыре квартала дисконтированного свободного потока операционного бизнеса, затем остаточную стоимость бизнеса по множителю годовой выручки. Это DCF с терминальной оценкой через multiple, а не полностью фундаментальная бессрочная DCF-модель.

Горизонт прогноза — один год. Прогноз не использует будущие шоки сценария. Он использует только текущую экономику компании:

- `g = clamp(state.growthBps, -2500, 3500)`;
- ARPU, переменные затраты на единицу и постоянные расходы фиксированы на горизонте;
- количество клиентов меняется с g каждый квартал;
- регулярные капитальные вложения вычисляются тем же способом, что в фактическом переходе;
- будущие разовые вложения неизвестны и в прогноз не включаются;
- никаких дивидендов, долговых поступлений или погашений внутри операционного DCF;
- для простой версии предполагаются уже созданные свободные мощности на год.

Прогнозный рост ограничивается, фактически заданный шок не обрезается. Так −34% подключений может произойти фактически, но прогноз дальнейшего сокращения ограничивается −25% за квартал. Это отдельное учебное допущение о нормализации темпа, которое делает оценку после большого падения мягче. +35% каждый квартал даёт примерно +232% за год, поэтому верхний предел — стрессовая граница модели, а не типичный устойчивый отраслевой рост. `growthBps` в кандидате хранит заданный темп спроса; фактический процент изменения целого числа клиентов может слегка отличаться из-за округления.

Точное дисконтирование с округлением только денежных результатов:

```ts
function value(state, parameters): bigint {
  const g = clamp(state.growthBps, -2500, 3500);
  let C = BigInt(state.customers);
  let pv = 0n;
  let num = 1n;
  let den = 1n;
  let lastMonthRevenue = 0n;
  for (let q = 1; q <= 4; q++) {
    C = applyBps(C, BigInt(g));
    const R = C * BigInt(state.arpuCents);
    const E = C * BigInt(state.unitCostCents) + BigInt(state.fixedCostsCents);
    const maintenance = roundDiv(3n * R * BigInt(parameters.maintenanceCapexBps), B);
    const fcf = 3n * (R - E) - maintenance;
    num *= B;
    den *= B + BigInt(parameters.discountBps);
    pv += roundDiv(fcf * num, den);  // отрицательные потоки НЕ обрезаются
    lastMonthRevenue = R;
  }
  const terminalEV = roundDiv(12n * lastMonthRevenue * BigInt(state.multipleBps), B);
  pv += roundDiv(terminalEV * num, den); // стоимость на конец q4
  const rawEquity = pv + BigInt(state.cashCents) - BigInt(state.debtCents);
  return rawEquity > 0n ? rawEquity : 0n;
}
```

`12 * monthRevenue` — годовая выручка. Если вместо этого использовать квартальную выручку, её множитель годового масштаба равен 4. Одновременное умножение квартальной выручки на 12 завысит terminalEV втрое.

TerminalEV — стоимость продолжающегося операционного бизнеса после четвёртого прогнозного квартала. Она не включает денежный запас и обязательства. Текущий cash добавляется один раз; debt вычитается один раз. Нельзя одновременно включить PV квартального FCF и ещё раз добавить накопленный из него будущий денежный остаток. Нельзя вычесть debt в каждом прогнозном периоде, а затем повторно вычесть ту же сумму в equity bridge. Финансирование не создаёт операционный доход: одинаковое увеличение cash и debt не меняет equity при прежних операционных данных.

Оценка `max(0, rawEquity)` — простое ограничение ответственности, а не полноценная оценка опциона собственников. Ноль требует отдельного контракта. В обычных игровых сценариях все оценки до решения должны быть строго положительными. Если допускается банкротство, следующий переход должен оставлять позицию обнулённой и запрещать новое вложение; нельзя превращать отношение с нулевым знаменателем в «доходность 0%» при восстановлении стоимости компании. Для выпуска сценариев с банкротством нужен отдельный продуктовый контракт; не вводить его молча.

Для положительной исходной оценки:

```text
returnBps = roundDiv((equityAfter - equityBefore) * B, equityBefore)
investmentAfter = roundDiv(investmentCents * (B + returnBps), B)
```

`returnBps >= -10000`. Квантизация доходности до bps означает, что результат игрока немного отличается от непосредственного отношения equityAfter/equityBefore; это предусмотренный единый контракт денежного расчёта, одинаковый для всех участников. Индекс графика и пояснение должны рассчитываться из тех же оценок, а не из независимо заданных чисел.

## 6. Реинвестиции и капитальные вложения

В основной модели дополнительные вложения из сценария оплачиваются в фактическом переходе. Положительный эффект может появиться через отдельно заданный рост клиентов или снижение unitCost. Само списание capex не создаёт произвольного роста оценки и не превращается в отдельный актив поверх terminalEV. Поэтому избыточное вложение без улучшения экономики снижает equity ровно на сумму вложения при прочих равных.

Отсутствие дальнейших инвестиций на расширение в прогнозе допустимо только как явно ограниченное допущение свободной мощности. Для VoltX и OrbitLink оно особенно сильное: реальное производство и спутниковая сеть имеют ограничения мощности, сроков ввода и обслуживания. Не представлять фиксированный процент maintenance как универсальную норму капиталоёмкости отрасли.

Если потребуется следующая версия модели, предложено одно из двух взаимоисключающих расширений:

1. Модель мощности: `customers <= capacity`; сценарные вложения заранее создают capacity с фиксированной задержкой. Прогноз перестаёт экстраполировать рост сверх доступной мощности.
2. Реинвестиции на прирост: `growthReinvestment = roundDiv(max(0, 12*(Rnext-Rprevious))*B, salesToCapitalBps)`, где знаменатель — учебное отношение годовой выручки к вложенному капиталу. Эти реинвестиции отражаются и в фактическом переходе, и в прогнозе. Из `extraCapex` исключаются уже учтённые вложения на то же расширение.

Формула второго варианта следует методике Damodaran, но конкретные значения salesToCapitalBps требуют отдельной калибровки. Не вводить её в середине мероприятия и не использовать для обратного решения желаемой доходности.

## 8. История, новости и отсутствие утечки

История состоит из seed и минимум четырёх уже завершённых квартальных переходов. Все точки содержат абсолютные показатели и индекс оценки; проценты вычисляются из соседних абсолютных значений. Начальный индекс 10000 соответствует выбранной baseline equity, а не утверждению об абсолютной стоимости компании 1000 $.

Сигналы до решения должны разделять проверяемый факт и план/риск: «опубликованный отчёт показывает рост расходов» — факт прошлого периода; «партнёр обсуждает расширение» — план. План не равен гарантированной будущей выручке. RU и EN должны сохранять одинаковую степень уверенности. Послераундовое событие описывает фактически применённые шоки и их последствия; не сообщать «затраты выросли», если конкретная вычисленная строка расходов снизилась.

Движок не читает будущий outcome при оценке текущего состояния. Сервер может заранее вычислить весь сценарий, однако API до решения выдаёт только текущий снимок, прошлые точки и доступные новости. `definition.shocks`, будущие состояния, outcomes и точные будущие доходности не должны попадать клиенту или в frontend bundle. Для истории используются исключительно synthetic company data; имена участников, пароли и локальные записи БД здесь не нужны.

## 9. Аудит кандидата реализации и изменения

Проверка чтением исходников выявила:

1. В первой прочитанной версии `nextBusinessState` списывал только `shock.capexCents`, а `equityValue` прогнозировал ещё регулярные вложения. Это давало фактическому бизнесу неоплаченное обслуживание. Рекомендовано вычитать `maintenanceCapex + extraCapex` в истории и игровых переходах. При повторном чтении `model.ts` исправление присутствовало: добавлены общий helper `maintenanceCapex` и аргумент parameters. Это подтверждение изменения формулы чтением, не результат теста.
2. Signed roundDiv корректно округляет положительные и отрицательные половины от нуля. Нельзя заменять его BigInt-делением без обработки знака: оно округляет к нулю.
3. В terminal используется месячная выручка, поэтому множитель 12 корректен. Добавление `cash-debt` вне PV корректно при принятом определении terminalEV.
4. В первой версии margin вычислялся косвенно через delta; повторно прочитанная версия использует прямой `roundDiv((R-E)*10000,R)`. Прямой вариант легче проверять и объяснять.
5. Кандидат округляет накопленный коэффициент дисконта до 1 bps на каждом квартале. Это воспроизводимая аппроксимация, но не точное дисконтирование. Рекомендованы BigInt num/den из раздела 5; они устраняют промежуточную погрешность почти без усложнения.
6. `returnFromEquity(before<=0)` возвращает 0. Это требует валидации положительной before equity всех допустимых игровых состояний. Без неё нулевая оценка и последующее восстановление не имеют корректного процента доходности. Игровое банкротство должно быть явно определено, если его решат разрешить.
7. `deltaBps(previous===0)` возвращает 0. Для финансового индикатора это неверная семантика «нет изменения», когда абсолютное значение выросло с нуля. Рекомендовано возвращать `null` для неопределённого процента либо гарантировать ненулевую базу соответствующего показателя. Не подменять это правило расчёта доходности.
8. Ограничение роста в DCF не должно переписывать фактический shock или скрывать фактические проценты. Ограничение относится только к предположению о следующем годе.
9. Полноценные проверки валидности BusinessState/Parameters/каталога должны выполняться до генерации: клиенты, деньги и затраты неотрицательные безопасные целые; discount положительный; multiple допустимый; параметры capex валидны. Один guard в valuation не проверяет весь входной контракт.

Самые существенные ограничения сохранённой простой модели — прогноз роста без дальнейшего расширения мощности, отсутствие оборотного капитала и процентов, сильная роль terminal multiple. Они явно описаны выше. Заданные coefficients не получены регрессией, не являются оценкой реального рынка и не должны так обозначаться в интерфейсе или документации.

## 10. Проверки перед принятием модели

Математические проверки:

- RoundDiv: `5/2 → 3`, `−5/2 → −3`, `1/3 → 0`, `2/3 → 1`; нулевой/отрицательный знаменатель отклоняется.
- Identity: для каждого исторического и игрового перехода `cashNext-debtNext-(cash-debt) = OCF-maintenance-extraCapex`; отдельно проверить переход через ноль и погашение дефицита.
- Один доллар дополнительных capex без прочих изменений уменьшает raw equity на 100 центов, если её обнуление не сработало. Не списывать тот же capex из cash и ещё раз из текущего equity.
- Увеличение cash и debt на одинаковую величину не меняет equity при прежнем операционном состоянии; debt не прибавляется к доходам.
- Увеличение unitCost/fixedCost не повышает операционную оценку при прочих равных; отрицательный FCF полностью вычитается из PV.
- Отраслевые параметры не должны превращать положительный рост клиентов в гарантированный положительный return: финансирование и затраты могут перевесить эффект.
- Проверка terminal: monthRevenue 100000 $, multiple 1,5 → terminalEV 1800000 $ до дисконтирования. Это фиксирует правильный масштаб 12.
- Ручной тест точного дисконта: плоская monthly revenue 100000 $, expenses 90000 $, maintenance 3%, discount 5%/квартал, multiple 1,5, cash 500000 $, debt 0, рост 0. Квартальный FCF 21000 $. При округлении каждого PV до цента получаем enterprise PV `155532941` центов, equity `205532941` центов. Следующий квартал с extraCapex 100000 $ оставляет cash 421000 $, equity `197632941` центов. При изменении порядка округления результат может отличиться на цент; порядок должен быть зафиксирован.
- Доходность при after=0 и before>0 равна −10000 bps. before=0 — явно отклонённое/отдельно определённое состояние.
- Повторная генерация каталога даёт одинаковый результат независимо от времени, игрока и его распределения.

Проверки данных и продукта:

- Каждый return, индекс истории, revenue/expenses change и пояснение воспроизводится из исходных состояний и shocks.
- Сигнал о концентрации GreenBox согласуется с платёжной единицей; события об отмене договоров, запуске и выручке не смешивают заявки с действующими подключениями.
- Никакое сравнение год к году из реального отчёта не выдается за такой же квартальный темп в игре.
- В каждом сценарии проверить все шесть компаний, все 3 раунда, RU/EN и полноту истории. Проверить сериализацию и отсутствие будущих данных.
- Проверить стратегии: равное распределение по шести; всё в каждую компанию; всё в cash; выбор по прошлой доходности; выбор по текущей марже; выбор по запасу денег; стратегия с полным знанием как недоступная верхняя граница.
- Проверить распределение победителей по сценариям, роль cash и устойчивость к вариации параметров ±10%. Не подбирать multiple и capex для восстановления прежней таблицы доходностей. Баланс допускается улучшать через экономически объяснимые параметры и новый scenario/modelVersion.
- Замерить долю terminalEV в enterprise PV. Если она доминирует, изменения multiple могут сильнее влиять на результат, чем операционные показатели: это нужно явно признать и проверить как отдельный риск обучения.
- Пользовательские пути, состояние локальной БД и обязательная браузерная проверка остаются в отчёте этапа реализации. Исследование не должно выдавать их за выполненные.

При принятии новых формул сначала закрепить единицы, параметры, округление и версии в математической спецификации и отчёте этапа. Сценарий, закреплённый за уже открытым мероприятием, должен сохранять исходную версию модели и данные. Новая версия используется для новых мероприятий; изменение функций не должно пересчитывать прошлые результаты.
